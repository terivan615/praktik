

### **Основные пользовательские роли:**
1.  **Инженер:** Решает типы инцидентов, выполняет рутинные операции, эскалирует сложные задачи.
2.  **Системный администратор:** Настраивает систему, управляет активами, решает сложные технические проблемы.
3.  **Конечный пользователь:** Сотрудник компании, который сообщает о проблеме или делает запрос (например, "не работает принтер", "нужен доступ к VPN").
4.  **Менеджер поддержки:** Контролирует SLA, распределяет нагрузку, анализирует метрики.

### **Ключевые клиентские пути**

#### **1. Путь Конечного пользователя (Employee)**
**Цель:** Быстро и без лишних усилий получить решение своей проблемы или ответ на вопрос.
*   **Этапы:** Осознание проблемы → Поиск канала поддержки → Создание тикета → Ожидание → Получение решения/решение → Обратная связь.
*   **Ключевые "боли":** Непонятные категории, сложная форма, долгое ожидание, необходимость дублировать информацию, отсутствие видимости статуса.
*   **Мультиканальность:** Email, веб-форма, телефон (с последующим созданием тикета менеджером).

| Этап | Задача пользователя | Точки контакта / Действия в системе | "Боль" / Возможность |
| :--- | :--- | :--- | :--- |
| **1. Осознание проблемы** | Понять, что проблема относится к компетенции IT отдела. | Внутренняя база знаний. | Не могу понять, куда обратиться. Статья не найденна или устарела. |
| **2. Создание тикета** | Описать проблему максимально четко. | Веб-форма, email, телефон. | Слишком много полей. Непонятные опции "Категория"/"Приоритет". Нет подсказок на основе истории. |
| **3. Ожидание** | Узнать, что тикет получен, и понять срок. | Автоматическое письмо-подтверждение, статус "Новый" в личном кабинете. | "Тикет утонул". Нет оценки времени решения. Непонятно, кто занимается. |
| **4. Взаимодействие** | Предоставить дополнительную информацию по запросу. | Уведомления в письме, комментарии в тикете. | Приходит десяток писем. Нет единого потока обсуждения. |
| **5. Получение решения** | Получить четкую инструкцию или подтверждение, что проблема решена на стороне инфраструктуры. | Комментарий/Решение в тикете, письмо. | Решение "Всё должно работать". Нет подтверждения со стороны системы. |
| **6. Закрытие и обратная связь** | Согласиться с решением или вернуть тикет на доработку. Оценить работу. | Кнопка "Решено"/"Не решено". | Неудобно нажимать ссылку в письме, чтобы оценить. Нет возможности легко создать тикет на ту же проблему, если она вернется. |

**Оптимизация:** Максимально простая форма с умными подсказками, прозрачный SLаймер, интеграция с аварийными системами (например, автоматическое создание тикета при сбое мониторинга).

#### **2. Путь Инженера**
**Цель:** Эффективно и по SLA обработать максимальное количество тикетов, эскалировать сложные, не тратить время на рутину.
*   **Этапы:** Получение нового тикета → Анализ → Действие (решение/команда) → Эскалация → Закрытие/Передача.
*   **Ключевые "боли":** Переключение контекста между десятками задач, ручной поиск информации по пользователю/активу, отсутствие готовых сценариев, сложности с эскалацией.
*   **Инструменты:** Досье пользователя, база знаний, скрипты, чаты для эскалации.


| Этап | Задача пользователя | Точки контакта / Действия в системе | "Боль" / Возможность |
| :--- | :--- | :--- | :--- |
| **1. Триаж и просмотр** | Быстро понять суть проблемы, критичность, историю пользователя. | Единая очередь, фильтры по SLA, приоритету. Карточка тикета. | Приоритеты выставляются низкокачественно. Нужно открывать 5 вкладок, чтобы понять контекст (AD, мониторинг, тиiket-история). |
| **2. Анализ** | Найти корневую причину, проверить связанные системы. | Доступ к данным, внешние интеграции (профиль пользователя в AD, статус сервера). | Информация разбросана. Нет единого "досье" на оборудование/сервис. |
| **3. Применение решения** | Выполнить действие (сбросить пароль, запустить скрипт, дать доступ). | Встроенные кнопки-"макросы", запуск внешних скриптов через API, встроенные сценарии. | Нужно каждый раз вручную выполнять 10 шагов из инструкции. Риск ошибки. |
| **4. Эскалация** | Передать тикет другой команде с полным контекстом. | Кнопка "Эскалировать" с выбором команды/специалиста. Автоматическое копирование всей истории. | Информация теряется при передаче. |
| **5. Коммуникация** | Информировать пользователя о статусе, запросить недостающее. | Быстрые шаблоны ответов, встроенный чат с пользователем. | Нужно каждый раз печатать похожие ответы. |
| **6. Закрытие** | Корректно закрыть тикет, заполнив нужные поля (время, решение). | Предзаполненная форма на основе действий. | Ручное заполнение полей для каждого закрытого тикета. |

**Оптимизация:** "Агентский рабочий стол" – единый интерфейс со всей информацией. Библиотека скриптов. Умные автоматические правила для эскалации.

#### **3. Путь Системного администратора**
**Цель:** Решать сложные, нестандартные проблемы, настраивать и обслуживать инфраструктуру и само приложение.
*   **Этапы:** Получение эскалированного/сложного тикета → Глубокий анализ (логи, тесты) → Изменение конфигурации → Внедрение исправления → Документирование решения.
*   **Ключевые "боли":** Нужен глубокий технический доступ к данным, работа с логами и конфигами, необходимость менять настройки самой системы, дублирование решений для похожих проблем.
*   **Инструменты:** логгирование, API для всех систем, возможность кастомизации workflow, конструктор отчетов, доступ к исходному коду.


| Этап | Задача пользователя | Точки контакта / Действия в системе | "Боль" / Возможность |
| :--- | :--- | :--- | :--- |
| **1. Принятие эскалации** | Получить полный контекст: что уже сделано, какие симптомы, доступ к каким ресурсам. | Тикет с полной историей. | Передача бессмысленна: "проблема с сетью", а IP-адрес и traceroute не вписаны. |
| **2. Диагностика** | Собрать и проанализировать технические данные (логи, метрики, конфиги). | Интеграция с Zabbix/Prometheus. | Логи на разных серверах. Нужно логиниться по SSH в каждую. Нет централизованного просмотра. |
| **3. Исправление** | Внести изменение в инфраструктуру. | Доступ к конфигурационным файлам. | Нужно зайти на сервер и править файлы вручную. Нет управления конфигурацией из системы. |
| **4. Откат / Внедрение** | Применить исправление в продакшене, убедиться в работоспособности. | Возможность создать задачу на изменение прямо из инцидента. | Изменение сделано "вручную", без записи в логи. |
| **5. Документирование** | Записать решение как новую статью в базу знаний или обновить существующую. | Обязательное поле "Решение" при закрытии. | Нет времени/мотивации писать статьи. Решение "забывается". |
| **6. Улучшение процессов** | Проанализировать повторяющиеся инциденты, предложить изменения. | Статистика по категориям, отчеты. | Нет инструментов для анализа. |

**Оптимизация:** Глубокие технические интеграции (API-first). "Инженерный режим" с доступом к логам. Мощная аналитика для трендов.

#### **4. Путь Менеджера поддержки**
**Цель:** Обеспечить выполнение SLA, сбалансировать нагрузку, улучшить качество сервиса и эффективность команды.
*   **Этапы:** Мониторинг → Распределение → Контроль → Анализ → Отчетность.
*   **Ключевые "боли":** Отсутствие дашбордов в реальном времени, ручное перераспределение, невозможность точно оценить нагрузку, сложные отчеты.
*   **Инструменты:** Дашборды, автоматические отчеты, настройки автоматического распределения.

| Этап | Задача пользователя | Точки контакта / Действия в системе | "Боль" / Возможность |
| :--- | :--- | :--- | :--- |
| **1.мониторинг в real-time** | Увидеть, сколько тикетов в очереди, какие на грани SLA, кто перегружен. | Единый дашборд с карточками: "Тикетов в работе", "SLA at risk", "Агенты: загружен/доступен". | Нужно постоянно переключаться между экранами. Нет "сигнальных" табло. |
| **2. Распределение нагрузки** | Перекинуть тикет с перегруженного агента на свободного или более экспертного. | Drag-and-drop между агентами, правила auto-assignment на основе skills/categories. | Приходится вручную искать свободного и звать его в чат. |
| **3. Контроль качества** | Проверить, что агенты корректно закрывают тикеты, используют KB, соблюдают процесс. | Гаджеты в тикете: "Использована KB-статья?", "Соблюден workflow?". Возможность случайного аудита. | Нет прозрачности actions агента. Качество измеряется post-factum на жалобах. |
| **4. Анализ эффективности** | Понять, где "узкие места": какие категории longest, какие агенты медленнее всего, где падает CSAT. | Интерактивные отчеты: "Time-to-resolution по категориям", "Сравнение производительности агентов", "Динамика CSAT". | Отчеты строятся неделю, потом в PDF. Нет возможности "покопаться" в данных и найти причину. |
| **5. Планирование ресурсов** | Оценить, сколько агентов нужно на следующий месяц, основываясь на volume and trends. | Прогнозирование на основе истории (целиکی, тренды, сезонность). | Оценка "на ощупь". Нет данных для аргументации под расширение команды. |
| **6. Отчетность для руководства** | Показать, как команда справляется, значение для бизнеса. | Готовые слайды: "Общее количество решенных инцидентов", "Соблюдение SLA", "Влияние на продуктивность бизнеса" (оценка). | Нужно вручную выagger данные из разных систем в Excel. |

**Оптимизация:** Умные, настраиваемые дашборды. API для выгрузки данных. Встроенные отчеты.

#### **5. Путь Администратора системы**
**Цель:** Легко настраивать и поддерживать саму систему под нужды организации.
*   **Этапы:** Настройка → Наполнение → Администрирование пользователей/прав → Кастомизация → Мониторинг здоровья системы.
*   **Ключевые "боли":** Сложные иерархии кастомизаций, риск "сломать" что-то при изменении workflow, долгое обучение администраторов, сложности с бэкапом/восстановлением кастомизаций.
*   **Инструменты:** Визуальные конструкторы workflow, диспетчер схем, API для автоматизации, ролевая модель, CLI/GUI для администрирования.

| Этап | Задача пользователя | Точки контакта / Действия в системе | "Боль" / Возможность |
| :--- | :--- | :--- | :--- |
| **1. Настройка** | Создать типы тикетов (Incident, Request, Problem), статусы, workflow, кастомные поля. | Визуальный редактор workflow (drag-and-drop). | Нужно копаться в XML-файлах. Сложные взаимосвязи между схемами. |
| **2. Наполнение данными** | Загрузить список категорий, служб, конфиги. | Импорт через CSV/Excel, API-интеграция с CMDB/AD/LDAP. | Ручной ввод сотен категорий. Данные дублируются. |
| **3. Управление пользователями и правами** | Назначить роли (Agent, Admin, User), группы, настроить права в рамках проектов/тикетов. | Интуитивная матрица ролей/разрешений, синхронизация с группами AD. | Сложная модель, в которой не разобраться. Чтобы дать право на одну кастомную вещь, нужно пробираться через 5 групп. |
| **4. Кастомизация под процессы** | Подогнать систему под собственный процесс. | Конструктор, автоматические правила. | Нет гибкости. Можно настроить только простые правила. Нет возможности вызвать внешний webhook или скрипт. |
| **5. Поддержка и мониторинг** | Убедиться, что система работоспособна, обновления прошли успешно, индексы не сбиты. | Health Check, логи приложений, мониторинг задач. | Нет понятных индикаторов. Обновление — стрессовая проверка всего после. |
| **6. Экспорт/Миграция конфигураций** | Перенести настройки. | Система конфигов, возможности экспорта-импорта схем. | Приходится заново настраивать эдентичные workflow в новой среде. Нет управления изменениями системы. |

**Оптимизация:** "Infrastructure as Code" для конфигов (YAML/JSON). Возможность клонирования проектов. Полноценная API для всех действий.

### **Кросс-пути и интеграционные моменты**

*   **Путь от инцидента к проблеме и изменению (Incident -> Problem -> Change):** Это ключевой цикл для админ/техподдержки. При продолжающемся или повторяющемся инциденте инженер создает **Problem Ticket**. Админ или инженер, создает **Change Request** для внедрения постоянного исправления. **Система должна связать эти три сущности.**
*   **Путь заявки на доступ (Access Request):** Рабочее место нового сотрудника → тикет "Заявка на доступ" → автоматическое согласование менеджером → тикет на создание учетной записи → исполнение (скрипт в AD) → закрытие.
